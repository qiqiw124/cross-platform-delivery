# Anti Patterns

## 1. 没有接口文档就直接开做
风险：
- 三端字段语义各自猜测
- 状态和错误码很容易跑偏

纠偏方式：
- 先列缺失字段和影响范围
- 最少补齐关键接口样例、字段类型、错误码

## 2. 只看设计稿，不看状态机
风险：
- UI 标准态能做出来，但空态、错误态、禁用态、重复进入态会错

纠偏方式：
- 强制补“状态图”或自行整理状态矩阵
- 把状态映射写进交付方案和回归清单

## 3. 只改某一端，不做跨端映射
风险：
- 前端、后端、客户端都自认为正确，但口径其实不一致

纠偏方式：
- 先输出字段/状态/埋点映射表
- 再进入各端实现

## 4. 联调问题不分层，直接猜代码
风险：
- 容易在错误的仓库里浪费时间
- 根因明明是接口口径，最后却在客户端修补

纠偏方式：
- 先分层：输入 -> 接口 -> 状态 -> 生命周期 -> 埋点
- 每层都给最小验证路径

## 5. 多仓库模式下没有归属表
风险：
- 一个需求在三个仓库里来回切换，最后没人知道哪项归谁改、归谁验

纠偏方式：
- 默认输出 ownership 表
- 每个验收点都标明仓库归属

## 6. 有业务变更却不更新 memory
风险：
- 下次排障和联调只能重新读代码
- 单人全栈时尤其容易重复踩坑

纠偏方式：
- 业务规则、埋点、缓存、生命周期变化都更新 shared/repo memory

## 7. 只做标准路径，不做异常路径验证
风险：
- 真正上线后最先出问题的往往是空值、缺字段、错误码、前后台切换

纠偏方式：
- 验收清单里强制列出异常 case
- 至少覆盖空态、错误态、弱网、前后台切换、重复触发
